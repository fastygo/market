# ADR-0029: Semantic class names generated at build time (no runtime class merge)

- Status: Proposed (owner t363u-t365u, 2026-11-25; design only, no code).
  Builds on ADR-0010 (SSR templ on UI8Kit), ADR-0018 (skins, white label),
  `.project/loadtest/2026-11-25.md` and `slo.md`.

## Context

The load test (2026-11-25, 1 vCPU) found `mergeTailwind` (UI8Kit,
vendored in `ui/kit`) at 43% of CPU on list pages. The owner postponed
memoization and asked for an optimization "out of the box": a build script
that turns utility chains into semantic classes with CSS `@apply`, so the
server writes fixed strings such as `button button-primary button-sm
button-cart` and never merges classes at runtime. Second goal: markup that
meets HTML5 / CSS3 / W3C standards. ui8px scope (owner t364u): ui8px checks
only primitives and mid-level prototype blocks; the app level (brand) may
override anything (contract `AGENTS.md`: "App screens are brand taste and
style: neither ui8px nor a spacing check scans them").

### How classes reach the markup today (commit c7b098c)

1. Recipes: `ui/kit/compose/compose.json` (generated by
   `codegen-x/ui8kit packages/kit-compose`, embedded) holds 50 cva-style
   recipes: `base`, `keys`, `byKey`, `defaults`, `compound`.
2. Compositions (`ui/kit/compose/*.templ`, e.g. `Button`, `Stack`, `Card`)
   call `Rc(id, values)`, which joins `base` + the chosen value of every
   axis + matching compounds (plain join, no merge), then appends the
   caller's `Class`.
3. Primitives (`ui/kit/ui/*/*.templ`, from `@ui8kit/codegen`) render
   `class={ XClasses(p) }` with `XClasses = uiutils.Cn(p.Class)` =
   `mergeTailwind` (`ui/kit/utils/cn_merge.go`, 309 lines: token split,
   variant prefix parse, utility group table, last-wins removal).
4. Organisms (`ui/kit/blocks/*.templ`, from `compose-gen` specs) build
   class strings with `orgutils.Cnv(...)` = the same merge (copy in
   `ui/kit/orgutils/cn_merge.go`) and pass them to compositions, which
   merge again in the primitive.
5. App screens (`internal/web/screens`, 21 files) pass utility strings in
   `Class:` (124 literals, 77 distinct, 99 distinct utilities; 2 dynamic:
   `avatarClass(size) + "..."`).
6. CSS: Tailwind CSS 4.3.3 CLI (`make css`), one entry per skin
   (`ui/styles/entries/<skin>.css`: skin -> `@import "tailwindcss"`,
   fonts, `kit.css`, `@source` = `ui/kit` + `internal/web/screens`),
   output `internal/web/static/skins/<skin>.css` (50.5 KB min, 9.7 KB gzip),
   committed and embedded (`//go:embed static`), served with
   `Cache-Control: public, max-age=3600` and no content hash.
7. `ui/kit` is generated code: `scripts/ui8kit.sh` reinstalls it with the
   pinned `ui8kit@3.5.0` CLI; `ui8kit.lock.json` pins file hashes; never
   edited by hand (ADR-0010).

### Inventory (instrumented render, 100 products, fake catalog)

Measured by wrapping `mergeTailwind` in a throw-away test (not committed):

| Route | merge calls / page |
| --- | --- |
| `/` | 2898 |
| `/catalog`, `/catalog/{slug}`, `/catalog?q=` | 2846-2848 |
| `/products/{slug}` | 2918 |
| `/authors/{slug}` | 2856 |

- About 28 merge calls per item card, 2.3 per element: every primitive
  evaluates `XClasses(p)` twice (`class={...}` and `if XClasses(p) != ""`),
  so half of the merge work is a codegen artifact.
- Distinct merge inputs over all routes: 97; distinct outputs: 94. The
  catalog page has 1223 `class` attributes with 47 distinct values;
  class attributes are 106 KB of 163 KB HTML (65%; gzip 5.4 KB).
- 83 of 97 distinct inputs (85% of 20 128 calls) are no-ops: the merge
  returns the joined input. Only 14 inputs drop a token:
  - 2 inside the kit: `MediaFrame` (`block` vs `hidden` on the dark image),
    `LucideIcon` in a button (`inline-flex` vs `inline-block`);
  - 12 app overrides: `Link variant=block` + `flex` over `inline-flex`,
    `text-lg font-bold` over the link size, `text-secondary-foreground`
    over `Title`'s `text-foreground`, `items-center` over Stack defaults,
    `flex w-full` over `grid gap-4` (form item), a ghost button size.
- Recipes: 50 recipes, 316 axis classes (269 with CSS; the rest are empty
  values such as `card variant=default`), 5 compounds, 298 distinct
  utilities, 83 arbitrary tokens (`[&>*+*]:mt-4`, ...).
- `@apply` probe (Tailwind 4.3.3, all recipes into
  `@layer components.kit`): everything compiles except 3 tokens: `group`
  and `peer` (markers, not appliable; used by `checkbox`, `disclosure`)
  and `hover:bg-destructive-hover` (no such token in our skins: today it
  silently renders nothing). Output: kit + theme + base 58.6 KB min,
  8.5 KB gzip.
- Render cost upper bound (benchmark, `/catalog`, 100 cards, dev machine,
  `mergeTailwind` replaced by a plain join): 12.4 ms -> 5.1 ms per page
  (-59%), allocations 75.0k -> 43.8k (-42%), 5.69 MB -> 3.67 MB.
- Not instrumented: `/account/*`, checkout (need PocketBase); static scan
  only.

## Decision

### 1. Naming convention

Two namespaces, never mixed:

| Layer | Pattern | Examples |
| --- | --- | --- |
| Kit (generated from recipes) | `ui-<recipe>`; `variant` axis: `ui-<recipe>-<value>`; other axes: `ui-<recipe>-<axis>-<value>` | `ui-button`, `ui-button-outline`, `ui-button-size-sm`, `ui-stack-gap-4`, `ui-image-aspect-video` |
| Kit organisms (generated from compose-gen specs) | `ui-<organism>`, `ui-<organism>-<part>` | `ui-product-card`, `ui-product-card-media` |
| App brand (hand-written) | `<block>`, `<block>-<part>`, `<block>-<modifier>`; never `ui-*` | `item-card`, `item-card-body`, `item-card-price`, `button-cart` |

- `ui-*` is the ui8px namespace for semantic classes (`.ui8px/patterns.json`,
  rule `UI8PX005` "unknown ui-* class"), so kit names are registered there
  and ui8px keeps validating them. The prefix also avoids clashes with
  Tailwind utilities: 7 recipe ids are Tailwind utilities or prefixes
  (`block`, `inline`, `grid`, `group`, `container`, `table`, `text-*`).
- Axis names are kept except for `variant`, because values repeat across
  axes (`default` exists in both `variant` and `size` of 19 recipes, so
  `ui-button-default` would be ambiguous). Values are used verbatim from
  the recipe (prop `Variant: "outline"` -> `ui-button-outline`), so the
  class maps 1:1 to the prop in all 9 runtimes. Characters outside
  `[a-z0-9-]` are replaced by `-` (`4/3` -> `4-3`).
- An axis value whose utility string is empty emits no class. Every other
  value, defaults included, emits its class (no hidden "default leaks";
  see open decision 3).
- State is not a class. Native and ARIA state selectors first, as rule 02
  already puts state on primitive props: `:disabled`, `:checked`,
  `[open]`, `:user-invalid`, `[aria-current="page"]`,
  `[aria-expanded="true"]`, `[aria-pressed="true"]`, `[aria-invalid="true"]`.
  Structural axes of organisms that are already data attributes stay
  selectors: `.ui-product-card[data-layout="horizontal"]`. No `is-active`
  style classes.
- Brand names must not start with `ui-` and must not be a Tailwind
  utility; the generator checks both (compile probe).

Before / after (rendered `class`, catalog page):

| Element | Before (after merge) | After |
| --- | --- | --- |
| Product card button, `Variant: "default"`, `Size: "sm"` | `inline-flex shrink-0 items-center justify-center whitespace-nowrap font-medium inset-ring transition-colors disabled:pointer-events-none disabled:opacity-50 rounded bg-primary ... h-8 px-3 text-sm` | `ui-button ui-button-default ui-button-size-sm` (+ `button-cart` if the app brands it; sold out = `disabled` attribute, styled by `:disabled`) |
| `ItemCard` root (`article`) | `flex h-full flex-col overflow-hidden rounded-xl border border-border bg-card text-card-foreground` | `item-card` |
| Card body `Stack Gap=2` + app `flex-1 p-4` | `flex flex-col gap-2 items-start justify-start flex-1 p-4` | `ui-stack ui-stack-gap-2 ui-stack-align-start ui-stack-justify-start item-card-body` |
| Title link `Link Variant=nav` | `inline-flex items-center underline-offset-4 gap-2 text-base font-semibold text-foreground hover:text-primary` | `ui-link ui-link-nav ui-link-size-default` |

### 2. Source of truth and generated CSS

- Kit: the recipes stay the single source (`compose.json`, compose-gen
  organism specs). A generator turns every recipe into rules with
  `@apply`, in recipe order: base, then axes in `keys` order, then
  compounds (`.ui-button-default.ui-button-size-sm` for a compound).
  Output: `ui/styles/generated/kit.css` plus the matching entries of
  `.ui8px/patterns.json` (name -> utilities).
- Within one axis the values are mutually exclusive. Across axes the
  generator compiles every rule and fails if two axes of one recipe set the
  same CSS property without a compound that resolves it (today the merge
  hides such overlaps; CSS would make them order dependent).
- `group` / `peer` markers are emitted as literal classes next to the
  semantic name (the only non-semantic tokens left), or replaced by
  `:has()` / sibling selectors upstream. Unknown tokens fail the build.
- The per-element token hooks of `ui/styles/kit.css`
  (`[data-slot="button"].rounded`, `[data-slot="card"].p-6`, ...) match
  utility classes and stop working once those classes leave the markup;
  they move into the generated rules (`.ui-card { padding:
  var(--pad-card, ...) }`). The unlayered rules of `kit.css` move into a
  layer, because unlayered CSS beats every layer, the brand layer included.
- App brand: hand-written `ui/styles/brand/<skin>.css` in
  `@layer components.brand`, `@apply` of any utilities and tokens; free
  styling, no 8+4 (app layer). One file per skin (ADR-0018), shared rules
  in `ui/styles/brand/common.css`.

### 3. Cascade layers (Tailwind v4)

Declared once in every entry, before `@import "tailwindcss"` (first
declaration fixes the order; verified with 4.3.3):

```css
@layer theme, base, components, utilities;
@layer components { @layer kit, brand; }
```

Order, low to high: `theme` (tokens) < `base` (preflight, kit base) <
`components.kit` (generated `ui-*`) < `components.brand` (app) <
`utilities` (escape hatch). Layer order beats specificity and source order,
so a brand class always wins over a kit class with no runtime merge; a
utility left in a screen (`sr-only`, `md:px-6`) wins over both.

Tailwind v4 notes:
- `@apply` works with variants, custom variants and arbitrary variants
  (`hover:`, `md:`, `dark:` = `&:is(.dark *)`, `disabled:`,
  `[&>*+*]:mt-4`); `--minify` (Lightning CSS) flattens the nesting.
- Rules in `@layer components` are always emitted (not tree-shaken);
  `@utility` would be tree-shaken and variant-capable (`md:ui-x`) but
  lands in the `utilities` layer and breaks the kit < brand order, so we
  do not use it for recipes.
- A stylesheet that uses `@apply` without importing Tailwind needs
  `@reference`; ours import it through the skin, so none is needed.
- `@source` keeps scanning `internal/web/screens` (app utilities);
  `ui/kit` scanning can be dropped once the kit emits only `ui-*` names.

### 4. Runtime: from merge to join

- Compositions: `Rc(id, values)` returns names, computed by the naming
  rule (string concatenation, no tables, no parsing).
- Primitives: `XClasses(p)` becomes a whitespace join of `p.Class`, and
  is evaluated once per element. Organisms: `Cnv` becomes a join.
- Caller `Class` is appended as is. Conflicts between kit and app are
  resolved by layers (section 3), never at runtime.
- This changes generated kit code, so it lands upstream in `codegen-x/ui8kit`
  as a per-target option (e.g. `ui8kit.config.json` `"classes":
  "semantic"` vs `"utilities"`), default `utilities`, so the other 8
  runtimes and other consumers keep the current API and DOM until they opt
  in. Component props do not change; only the rendered `class` value does.
  Until upstream ships, see open decision 2.

### 5. Build integration and CI

- `go generate ./ui/...` (or `make uicss`) runs the generator, a build-time
  Go tool under `scripts/uisem` (no Node at runtime, ADR-0010): reads
  `compose.json` and organism specs, writes `ui/styles/generated/kit.css`
  and `.ui8px/patterns.json`; then `make css` compiles the skins.
- `make verify` and CI: regenerate into a temp dir and `diff` against the
  committed files (fails when stale); `templ generate` diff as today;
  compile every skin with `--minify` (fails on unknown `@apply` tokens).
- CSS URL gets a content hash (`/static/skins/storeee.css?v=<sha256[:12]>`,
  computed at start from the embedded file) so a deploy never pairs new
  HTML with a cached old stylesheet (today `max-age=3600`, no hash).

### 6. Validation

- HTML: Nu HTML Checker (`vnu.jar`, W3C) on rendered pages of every route
  in CI (home, catalog, product, author, account sign-in, checkout,
  notice); zero errors gate.
- CSS: W3C CSS Validator as a report. It flags valid modern CSS that
  Tailwind v4 emits (`@layer`, `@property`, `color-mix()`, `oklab`) [?
  to be confirmed on first run]; we gate on our own rules (generated kit
  and brand files) with an allowlist of those features, not on the
  Tailwind preflight.
- ui8px: unchanged scope. It reads `@apply` in `.css`, so
  `ui/styles/generated/kit.css` is linted (8+4 by scope: controls vs
  layout) and `UI8PX005` validates every `ui-*` name in templates against
  `patterns.json`. Brand CSS and screens stay out of the scan (app layer).
- Golden test: render each route with the fake catalog and assert that
  every class in the HTML exists in the compiled CSS (catches typos and
  dead names), and that no utility-looking token comes from `ui/kit`.

### 7. Migration plan (small steps, each green and deployable)

1. Measure and generate, no behavior change: commit the inventory test
   and the render benchmark (test only); add `scripts/uisem`,
   `ui/styles/generated/kit.css`, `patterns.json`, layer declarations, CI
   freshness check. The new CSS is present but unused.
2. Brand layer: move app screens from utility `Class:` strings to brand
   classes, starting with `ItemCard` (the hot path) and the 12 conflicting
   overrides; keep single utilities where they are the clearest
   (`sr-only`). Visual diff by screenshots of each route.
3. Kit switch (upstream option or open decision 2): compositions and
   organisms emit `ui-*`, primitives join, `XClasses` evaluated once;
   token hooks moved from `kit.css`; CSS content hash. Golden test on.
4. Drop `@source "../../kit"`, remove dead utilities, rerun the load test,
   update `slo.md` thresholds.
5. Brand skins (StorEEE, GoDudY) as `brand/<skin>.css` over the same
   markup.

### 8. Expected gain and how we measure

- Upper bound from the benchmark: about -59% render CPU and -42%
  allocations on a 100-card list page; on the 1 vCPU host, with
  `mergeTailwind` at 43% of CPU, list page throughput up to about 1.75x
  (1 / 0.57) where rendering dominates [? DB time limits the catalog].
- HTML: class attributes are 65% of the catalog HTML; semantic names
  should cut raw HTML by roughly half [?], gzip size changes little.
  Less HTML also means less write time in templ.
- Measurement: `scripts/loadtest` with the same seed (10 000 products),
  `GOMAXPROCS=1`, c=16 and c=1, scenarios home, catalog, product, search;
  CPU profile (`/debug/pprof/profile` on loopback) before and after:
  `mergeTailwind` must be 0%; templ render histogram p95/p99 from
  `/metrics`; results in `.project/loadtest/<date>.md`.

## Consequences

- No runtime class merging and no merge code on the hot path; class
  conflicts become a build-time concern (generator checks, layers).
- Markup gets short, readable, stable names; state lives in HTML and ARIA
  attributes, which also serve assistive technology.
- The kit stylesheet always contains all recipe rules (about 270), even
  unused ones; acceptable at about 8.5 KB gzip, prunable later by a usage
  scan.
- The generator becomes a build dependency to maintain next to Tailwind;
  recipe changes upstream need a regenerate (CI catches a stale file).
- Visual regressions are possible where the merge silently fixed overlaps;
  steps 2 and 3 need screenshot review per route.
- Memoization (postponed by the owner) becomes unnecessary for the kit; it
  may still help dynamic app strings such as `avatarClass(size)`.

## Risks

- A local fork of generated kit code drifts from upstream and from the
  other 8 runtimes (identical DOM rule): mitigated by the upstream option.
- Cross-axis property overlaps inside a recipe become order dependent:
  the generator check fails the build.
- Unlayered rules in `kit.css` and the `[data-slot].utility` token hooks
  would override or stop matching: moved in step 3.
- Stale CSS after deploy: content hash on the stylesheet URL.
- W3C CSS Validator false positives on Tailwind v4 output: report, not a
  blind gate.

## Decisions needed from the owner

1. Prefix: `ui-*` for kit classes (recommended: ui8px namespace,
   `patterns.json`, no clash with Tailwind) and bare names for brand
   classes, or bare names everywhere as in `button button-primary` (clashes
   with `block`, `grid`, `group`, `container`, `text-*`).
2. Where the kit switch lives: upstream option in `codegen-x/ui8kit` for
   the templ target (recommended; other runtimes unchanged) or a local
   post-install patch of `ui/kit` in this repo first (faster, but breaks
   "never edited" and the lock hashes until upstream catches up).
3. Defaults: always emit the class of a non-empty default value
   (recommended: `ui-stack-align-start` visible, no leaks) or fold
   defaults into the base rule for shorter markup (`ui-button
   ui-button-size-sm` instead of `ui-button ui-button-default
   ui-button-size-sm`), which needs a generator check that every other
   value overrides every property the default sets.
